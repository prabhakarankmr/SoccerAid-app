## 1. Golden Rule — The App Is a Thin Client

**No business logic in the app.** The app:

- **sends intents** (e.g. "pass from P1 to P2", "shot on target", "undo") to `POST /api/v1/matches/:id/events`;
- **renders state** returned by the API or pushed by the WebSocket (score, clock, possession, stats, timeline, standings, awards);
- **shows the next modal** the server asks for via the `prompt` field in the event response.

The app must **never** compute: score, stats, assists, possession time, match clock, standings/points table, leaderboards, awards, formations' default coordinates, fixture generation, or validation of football rules. If you are writing an `if` about football rules in the app, it belongs in the backend.

Allowed client-side logic: UI state (which modal is open, selected tab), input validation for UX (required fields), formatting (`mm:ss`), rendering a running clock **between** server updates from `clockStartedAt + elapsedSec`, and the offline queue.

> The reference project (`E:\football-match-tracker`) does all logic in `components/match-setup.tsx` (~2000 lines of `useState` + stat maths). **Copy its UI, not its logic.**

## 5. Screens (must match the reference UI)

### 5.0 Authentication & Onboarding (no reference equivalent — new for this app)

Signup is **India-only**, phone + OTP. OTP send/verify happens entirely on-device via Firebase
Phone Auth (`src/api/firebasePhoneAuth.ts`); the app never talks to the backend's OTP endpoints
because there aren't any (see BACKEND_INSTRUCTIONS.md §9.5) — it posts the resulting Firebase ID
token to `POST /auth/firebase/verify` and gets back the app's own access/refresh token pair.

- **`(auth)/login.tsx`** — shows the app logo (`assets/logo.png`, decorative — `accessible={false}`,
  the heading text carries the actual meaning for screen readers) above the form. Single input, static `+91` prefix, 10 digits, validated client-side
  against `^[6-9]\d{9}$` (UX only — the real constraint is enforced server-side on the verified
  Firebase `phone_number` claim). Calls `sendOtp(phone)`, then pushes to `otp` with `phone` as a
  route param.
- **`(auth)/otp.tsx`** — 6-digit input. Calls `confirmOtp(code)` (Firebase) to get an ID token,
  then `POST /auth/firebase/verify`. On success, stores the token pair (`useAuthStore.setTokens`)
  and routes: `isNewUser` → `profile-setup`, else → `(tabs)`.
- **`(auth)/profile-setup.tsx`** — display name (required), username (required, unique — regex
  `^[a-z0-9_]{3,20}$` client-side mirrors the backend's, auto-lowercased/filtered as typed, same
  pattern as the phone digit input on `login.tsx`), bio (optional, 160 chars), preferred position
  (optional). Letter-avatar placeholder above the form (first letter of display name, or `?`) —
  not a stub, the permanent no-photo state; real upload comes later per the user's own plan, at
  which point `avatarUrl` (already on `User`, BACKEND_INSTRUCTIONS.md §4) just needs a value.
  `PATCH /me`; a `USERNAME_TAKEN` response (`ApiError.code`) shows inline under the username field
  specifically, distinct from the generic save-failed message. On success seeds the `me` query
  cache directly (`setQueryData`, no refetch) and routes to `(tabs)`.
- **`app/index.tsx`** — the auth gate. Hydrates `authStore` from SecureStore, then `<Redirect>`s to
  `(tabs)` if a refresh token exists, else `(auth)/login`. Every other screen assumes this gate
  already ran.

Known shortcut: these three screens use raw `TextInput`/`Pressable` directly instead of the
`ui/Button` / `ui/Input` component library (§7, still TODO) — revisit when that library exists
instead of copying the inline pattern into new screens.

### 5.1 Match Setup — `match/new.tsx` (ref: `match-setup.tsx` step `teams`)

**Implemented** (2026-10-26), though the team-selection UI diverges from the original
ref-matching plan below — see the note at the end.

- Header: outline "← Back to Dashboard".
- Title **"New Match Setup"** (`text-2xl text-emerald-800`), subtitle switches between "Start by
  picking both teams." and "Now pick the format and formations." (`text-emerald-600`).
- **Team A** / **Team B** slots side by side (`TeamSlot`, inline in the route file): a letter-
  avatar circle (`+` until picked) + the team's name, tap either to open the shared `TeamPicker`
  (§7) with `title="Select Team A"`/`"Select Team B"` — both slots use the exact same picker,
  neither is restricted to "your teams only" (you might be setting up a match for a team you
  don't own, on either side).
- **Progressive reveal** (user call, 2026-10-26): everything below — format, formations,
  duration, extra time/penalties, the submit button — stays hidden (`bothTeamsSelected`, not a
  separate step/route) until both Team A and Team B are chosen and distinct. The first thing
  the screen shows is only the two team slots; picking teams is a prerequisite for the rest to
  even make sense (formations depend on nothing about the teams, but showing nine more controls
  before the one actually-required first choice is made read as "too much at once").
- **Players per side**: pill row from `GET /meta/formats` (`useFormats`, §6.2) — "3v3" … "11v11".
  Picking one resets both formation selections (a formation from the old size is meaningless at
  the new one).
- **Formation**, once a size is picked: two separate pill rows, one per team ("{team name}'s
  formation"), both from `GET /meta/formations?playersPerSide=` (`useFormations`) — `formationHome`
  and `formationAway` really can differ, it's not one formation for the match.
- **Half duration**: pill row, 5–45 min presets (not free-entry — a season of casual 5-a-side
  games doesn't need arbitrary durations, and presets can't produce an invalid value).
  **No extra time / penalties toggles** — removed (user call, 2026-10-27; they were there from
  the start but never actually asked for). `POST /matches`' DTO still accepts `extraTimeSec`/
  `hasPenalties` (both optional — backend unchanged, §7.2), the frontend just never sends them
  now; a match is always level-at-full-time with neither.
- Full-width primary button **"Set Up Players"** (disabled until both teams, format, both
  formations and a duration are chosen, and the two teams aren't the same team) → `POST /matches`
  (`useCreateMatch`) → `router.replace` to `match/[id]/lineup`.
- Tournament linking (`tournamentId`) is accepted by the backend DTO but has no picker here —
  tournaments aren't built yet (§5.6); this is standalone-match creation only for now.

**Diverges from the original plan above on team selection**: the original spec was a plain
"select existing team or enter new" dropdown per slot. The actual team picker (`TeamPicker`,
§7) is a full-screen 3-tab modal — **Your Teams** / **Opponents** / **Add** — with a search bar
matching name, code, or the team's captain's phone/username, and a QR-scanner shortcut that
resolves _any_ team by code via `GET /teams/by-code` (not scoped to owned/opponent teams, since
scanning is specifically for a team you have no prior relationship with yet). This was a
deliberate, explicit user request (2026-10-26), not a reference-matching screen — kept both
teams' pickers identical (neither slot is "must be mine") since the reference's Team A/B split
doesn't map cleanly onto "which team do I actually own."

Picking a team in `TeamPicker` doesn't immediately fill the slot either (2026-10-27, also user
call): it opens that team's **roster step** — the team name as header, a search box that
filters its current players client-side, and (owner-only) an **Add** button opening
`AddPlayerPanel` (§7) to add an existing app user or create a guest, same two-path flow as
`teams/[id].tsx`. Every path that lands on a team — tapping it in the list, a successful QR
scan, or finishing the "Add" tab's create form — goes through this same roster step rather than
closing immediately, so a team that's short of players for the chosen format can be topped up
without leaving match setup. "← Back to teams" returns to the list without losing the
in-progress Team A/B selections already made.

Each player row is also tappable to mark them **playing or not** for this specific match
(2026-10-27, user call — "options to select players who is going to play") — a lightweight
pre-filter, distinct from and prior to the detailed starter/sub/goalkeeper assignment that
happens later on `match/[id]/lineup.tsx` (§5.2). A team's full roster can list more people than
show up to any one game, so this narrows the candidate pool before the real lineup work starts.
State is **who's deselected**, not who's selected (`deselectedPlayerIds`, not
`selectedPlayerIds`) — defaulting to "everyone on the roster is playing" needs no
initialization from the async roster fetch at all, which sidesteps a `react-hooks/set-state-in-effect`
lint error the naive version hit (deriving the opposite set would need a `useEffect` to seed it
once the roster loaded, syncing React state from a query result — exactly the "effect smell"
pattern the lint rule flags). A player added mid-session via `AddPlayerPanel` is automatically
"playing" for the same reason — they're simply never in the deselected set to begin with, no
extra bookkeeping needed. **"Use This Team"** (disabled if nothing's selected, shows the count
once something is) is what actually calls `onSelect(team, playerIds)` and closes the picker —
`playerIds` is the roster filtered down to the non-deselected ones at confirm time, not a
running list maintained some other way.

`match/new.tsx` carries `homePlayerIds`/`awayPlayerIds` (`string[]`, one per side) from
`TeamPicker`'s `onSelect` through to `POST /matches`' success navigation as comma-joined route
params on `match/[id]/lineup`. That screen (§5.2) filters each team's roster down to just those
ids before offering them as starter/sub candidates — `filterAvailable()`, falling back to the
full roster if the params are missing (e.g. a direct link to an existing match, or one set up
some other way) rather than showing nobody.

### 5.2 Player Setup — `match/[id]/lineup.tsx` (ref: step `players`)

**Rebuilt 2026-10-27** around the real `pitch/FootballPitch` (§7) — supersedes the 2026-10-26
list-based version entirely (user call, reference screenshots of a more mature pitch-based
lineup UI: "match setup page should look like this... swap player position and goalkeeper
edit"). `GET /matches/:id` (`useMatch`) for teams/format/formations, `GET /teams/:id` (`useTeam`,
§5.9) for each side's roster, `GET /meta/formations?playersPerSide=` (`useFormations`, §5.1) for
the slot layout. Available players per side start from `homePlayerIds`/`awayPlayerIds` route
params (who was marked "playing" on `TeamPicker`'s roster step, §5.1) — falls back to the full
roster if those are absent.

- **Start Match** sits near the top (under the subtitle), not at the bottom — matches the
  reference, and stays reachable without scrolling past the roster panel/pitch. Disabled until
  both sides have exactly `playersPerSide` filled slots (which, since there are exactly that many
  slots per side, also guarantees exactly one goalkeeper each — no separate GK check needed).
- **"Manage/Hide Team Rosters"** collapsible section (collapsed by default), two columns, one
  per side: team pill + "assigned/needed" count (e.g. "5/6"), every available player as a row
  with a **GK** badge if they currently hold the goalkeeper slot, and an swap icon
  (`arrow-left-right`) — tap one player's icon then another's **on the same side** to swap their
  slot assignments (works whether either is on the pitch or benched). Each column also has an
  **"+ Add Guest"** row (name only, same `POST /players` + `POST /teams/:id/members` mechanism
  as `AddPlayerPanel`/`CaptainPicker`, §7, but implemented inline here rather than reusing those
  components — this flow only ever needs the guest half, not `MemberLookup` too) — added
  immediately to that side's available pool, no refetch required before it's usable.
- **The pitch** (`FootballPitch`, §7): one continuous pitch, not two side by side — Team A (home)
  on the right half, Team B (away) on the left, mirrored from the same formation-slot data
  (`posY`: 100 = that side's own goal, 0 = the opponent's). Filled slots render a draggable
  `PlayerToken`; empty ones render a dashed `EmptySlot` that assigns the next benched player on
  tap. **Dragging** a token (real pan gesture, `react-native-gesture-handler` +
  `react-native-reanimated`, both already dependencies) swaps it with whichever slot on the
  _same side_ is nearest to the drop point — including empty ones. **Tapping** a token makes
  that player the goalkeeper (swaps them into the GK slot; a `Gesture.Tap().maxDistance(8)`
  composed via `Gesture.Race` with the pan gesture is what lets both live on one token without
  the drag claiming every touch — RNGH's own tap primitive, not a nested RN `Pressable`, which
  wouldn't reliably receive touches inside a `GestureDetector`).
- Slot assignment state is **derived, not effect-seeded**: `overrides: SlotAssignments | null`
  per side, `null` meaning "use the computed default" (available players queued into slots, GK
  first) — the same pattern as `TeamPicker`'s `deselectedPlayerIds` (§5.1), chosen for the same
  reason: no `useEffect` needed to initialize state from the async roster fetch, so no
  `react-hooks/set-state-in-effect` risk. Any swap/assign/guest-add seeds `overrides` from the
  current _effective_ (default-or-overridden) state, not from a stale snapshot.
- Submission (`toLineupPayload`): iterates each side's formation slots **in slot order** —
  this is the whole reason no backend change was needed to support arbitrary on-pitch
  arrangement. The backend's own default-position logic (`BACKEND_INSTRUCTIONS.md` §7.2) assigns
  outfield slots to submitted entries _in submission order_; since the frontend's slot order
  comes from the exact same `GET /meta/formations` generator the backend uses, submitting in
  that order makes the backend's assignment land on the slot the player was actually dragged to,
  with zero new API surface. Unassigned-but-available players are appended as `isStarter: false`
  substitutes. On success → `match/[id]/live` (§5.3, still a stub).

**Not built this pass**: the reference screenshots also showed a "Landscape View" toggle
(`expo-screen-orientation` is already a dependency, so a simple lock/unlock would be low-effort)
— left out as a separate concern from what was actually asked (swap positions, edit goalkeeper),
not a hard blocker, worth a follow-up if the portrait pitch feels cramped in practice. Also
worth flagging: the drag gesture's feel (snap distance, animation timing) is untested by human
hands — verified by typecheck/lint/`expo export --platform web` only, which confirms it builds

## 6. Data Layer

### 6.1 API client

- Base URL `${env.API_URL}/api/v1` — **version lives in one constant** (`API_VERSION = 'v1'`).
- Generated client from `${API_URL}/api/docs-json` via `npm run api:generate`; commit generated code; regenerate whenever backend contract changes.
- Interceptors: attach `Authorization: Bearer`, `X-Request-Id`, `Idempotency-Key` on POST/PUT; on 401 refresh once then retry; map error envelope `{ error: { code, message } }` to a typed `ApiError`.
- Show user messages by `error.code` (map in `src/api/errorMessages.ts`), never raw server text.

**Current state (§5.0):** `src/api/client.ts` implements the base-URL/bearer/401-refresh-retry/`ApiError`
pieces by hand with plain `fetch`, since there's no generated client yet (nothing to generate from
until a non-auth endpoint exists). No `X-Request-Id`/`Idempotency-Key` headers yet — add when the
first idempotent write (match events) lands. `errorMessages.ts` mapping is also TODO; screens show
a generic retry message for now.

### 6.2 TanStack Query

- Query keys factory in `src/api/queryKeys.ts` (`matchKeys.state(id)` …). No inline string keys.
  Implemented so far: `meKeys`, `teamKeys` (`owned`/`opponents`/`detail`, all under the `'teams'`
  prefix — `invalidateQueries({ queryKey: ['teams'] })` after a mutation catches all three,
  TanStack Query matches by key prefix, not exact equality), `playerKeys`.
- `staleTime` 30 s default; match state is kept fresh by sockets (`setQueryData`), not by polling.
- Persist selected queries to MMKV for fast cold start.

### 6.3 Sending match events (`useSendEvent`)

1. Build `{ clientEventId: uuid(), expectedSeq: state.lastSeq, type, ... }`.
2. Put it in the **MMKV offline queue** first, then send.
3. Optimistic UI is limited to a "pending" indicator on the action — **do not** change score/stats locally.
4. On 200: `setQueryData(matchKeys.state(id), res.state)`, remove from queue, open `res.prompt` modal if present.
5. On 409 `MATCH_SEQ_CONFLICT`: replace state with server state, drop the stale event, toast "Match updated on another device".
6. On network failure: keep in queue; flush in order when online (same `clientEventId` ⇒ server dedupes). Show an "Offline – n events pending" chip.

### 6.4 Realtime (`useMatchLive(matchId)`)

- Single socket instance (`/v1/live`, `transports: ['websocket']`, JWT in `auth`).
- On focus: `match:subscribe`; on blur: `match:unsubscribe`.
- `match:state` / `match:event` → `setQueryData`; if `seq` gap detected → refetch `/state`.
- `tournament:standings` → update standings query.
- Reconnect with backoff; on reconnect re-subscribe and refetch state.

## 9. Coding Standards & Code-Review Rules

- TypeScript `strict`, no `any`, no `@ts-ignore` without linked issue.
- ESLint (expo config + typescript-eslint strict + react-hooks + react-native a11y) + Prettier; Husky + lint-staged; Conventional Commits.
- Styling only with NativeWind `className`; no inline `style` except dynamic values (pitch coordinates, animations). No hard-coded hex — use tokens. Exception found in practice: `h-*`/`w-*` sizing classes did not apply to `<Image>` in `(auth)/login.tsx` — it rendered at the asset's intrinsic pixel size instead (filled the screen) — so that one image sizes itself via `style={{ width, height }}` instead. If you hit the same thing elsewhere, same fix; this isn't a one-off exception to copy preemptively, only apply it where `className` is confirmed not to size the element.
- Components are pure/presentational; data via hooks. No `fetch` in components.
- Memoise list items (`React.memo`), use `FlashList` for lists > 20 rows, avoid re-rendering the pitch on every clock tick (clock is its own component).
- Accessibility: every pressable has `accessibilityLabel`; touch targets ≥ 44 px; colour is never the only indicator (icons + text for teams).
- **Every screen with a `TextInput` wraps its form in `KeyboardAvoidingView`** (`behavior={Platform.OS === 'ios' ? 'padding' : undefined}`) — without it the keyboard covers whichever field is focused instead of the screen shifting it into view. Forms too tall to fit above the keyboard on a small device (more than ~2 fields, or any `multiline` field) additionally need a `ScrollView` inside it (`keyboardShouldPersistTaps="handled"`, content padding/centering via `contentContainerClassName`, not `className` directly — that styles the scroll viewport, not its content). If the screen also sits inside `(tabs)/_layout.tsx`'s floating pill tab bar: that bar is `position: absolute`, so unlike a normal docked tab bar it does **not** get pushed up with the keyboard — it ends up stranded on top of it instead. `(tabs)/_layout.tsx` hides it for the duration via `Keyboard` listeners (`keyboardWillShow`/`Hide` on iOS, `keyboardDidShow`/`Hide` elsewhere) toggling `tabBarStyle.display`; no-op on web, which has no on-screen-keyboard-over-content problem to begin with. Reference implementation: `(tabs)/profile.tsx`'s edit mode, `(auth)/profile-setup.tsx`.
- Error/empty/loading states on every screen (skeletons, "No events recorded.").
- Tests: component tests for pitch, action bar, modals; hook tests for `useSendEvent` (queue, 409, retry); Maestro E2E: create match → lineup → score goal → undo → end → summary.

### 11.1 Phone OTP login on web (resolved via a separate implementation)

`@react-native-firebase/auth`'s web shim (`dist/module/web/RNFBAuthModule.js`) rejects
`signInWithPhoneNumber()` unconditionally with `unsupported` — not a missing-config error, the
library simply never implemented it for web. So web does **not** go through RNFB at all: it uses
the plain `firebase` JS SDK directly (`src/api/firebasePhoneAuth.web.ts`), which Metro picks
automatically over `firebasePhoneAuth.ts` when bundling for web (same per-platform-file mechanism
as `expo-secure-store`'s own `.web.ts`). Consequences of that split:

- Needs its own Firebase app config — `firebaseWebConfig` (`src/config/env.ts`,
  `EXPO_PUBLIC_FIREBASE_WEB_*` vars, §11). Native reads `google-services.json`/
  `GoogleService-Info.plist` instead and never touches these.
- The web SDK's phone auth requires a reCAPTCHA verifier bound to a real DOM node — `(auth)/login.tsx`
  renders `<View nativeID="recaptcha-container" />` (web-only; `nativeID` → DOM `id` under
  react-native-web) for `firebasePhoneAuth.web.ts` to attach an invisible `RecaptchaVerifier` to.
  The container id is duplicated as a literal in both files rather than imported — `tsc` always
  type-checks the base (native) `firebasePhoneAuth.ts`, which doesn't export it, so importing it
  across the platform-file boundary would fail type-checking even though Metro would bundle fine.
- Both files export the same `sendOtp(e164Phone)` / `confirmOtp(code): Promise<string>` shape, so
  every call site (`(auth)/login.tsx`, `(auth)/otp.tsx`) is platform-agnostic.

If this ever breaks again, don't assume it's the same RNFB limitation — check which file Metro
is actually resolving to first.

Related: `expo-secure-store` also has no web implementation (`ExpoSecureStore.web.ts` is a literal
`export default {}` stub — calling it throws `getValueWithKeyAsync is not a function`). Worked
around in `src/stores/secureStorage.ts`, which every token read/write goes through instead of
calling `expo-secure-store` directly: native uses SecureStore as normal, web falls back to
`localStorage` (fine for dev-preview session persistence; web was never going to have real secure
storage anyway). Route any new secrets-at-rest through that wrapper, not `expo-secure-store` directly.

### 11.2 `tsc` needs a larger Node stack size than the default

Plain `tsc --noEmit` started crashing with `RangeError: Maximum call stack size exceeded` once
the project grew past a certain size — not from any one file being pathological (confirmed by
bisecting file-by-file: the crash point moved around depending on what else was in the project,
and briefly looked like it was about `lucide-react-native/icons/*` subpath type declarations
specifically until removing _those_ didn't fix it either). The actual cause: Node's default V8
stack size is tight on Windows, and this project's type-checking recursion depth crossed it.
Confirmed by running `node --stack-size=8000 ./node_modules/typescript/lib/tsc.js --noEmit`
directly — passes clean. The `typecheck` script (§11) now invokes `tsc` that way instead of via
the `tsc` bin shim, which doesn't have a way to inject the flag. If this starts failing again as
the project grows further, raise `--stack-size` rather than assuming it's a code regression —
check with a quick `node --stack-size=<bigger> ./node_modules/typescript/lib/tsc.js --noEmit`
before spending time bisecting files.
